# 时序多数投票修复断灯条歪框 —— 说明（2026-11-26）

## 一句话结论

我实现了方案 A（时序多数投票），**全 1770 帧 A/B 验证通过**：框数变化 0、中心位移 0、
没有把任何正常板弄丢或弄歪；整段视频 72 处"远处断灯条板"被正确修正框高，
第 157 帧距离从 3.30m 修正到 3.15m。**默认仍是关闭的**，你确认效果后按需开启。

---

## 一、为什么上一轮"调参数"全部失败，这一轮却成了

上一轮试过 4 种纯单帧方案（放宽合并间隙、竖直闭运算、取较长、差值阈值），
全部误伤别的帧。根因是：**单帧里"灯条断了"和"车斜着把灯条拍短了"特征完全一样**，无法区分。

这一轮加了"时间"这个新维度后，发现一个关键事实（用数据测出来的）：

> 第 157 帧那块板，两根灯条高度比 ratio **一直稳定在 0.62~0.67**，
> 不是那一帧突然断的——它整段视频都是一长一短（27px vs 42px）。

所以正确思路不是"检测突然变短"，而是：
- **真断裂** = 一直稳定地一长一短，且是远处小板 → 该修；
- **斜视角板** = ratio 极低（≈0.34）或忽远忽近波动大 → 不能碰。

这就是时序信息带来的新判据，是单帧方案做不到的。

---

## 二、判据怎么设计的（讲给小白听）

对每一块板，记录它最近若干帧的"两根灯条高度比 ratio = 短的/长的"，然后看三件事：

1. **历史中位数落在 0.54~0.78**？—— 这是"一长一短但没到极端"的区间。
   - 正常对称板 ratio>0.78，排除；
   - 极端斜视角板 ratio≈0.34，落在下界外，排除。
2. **历史标准差 ≤ 0.08**？—— 说明它"一直如此、很稳定"，不是忽大忽小乱跳的板。
3. **较长那根灯条 ≤ 55px**？—— 真断裂的是远处小板（≈42px）；
   近处大板（≈89px）一长一短多是透视，不能修。

三条全满足 → 判定为"持续断裂" → 用**当前帧较长的那根灯条**重建四角点，重算 PnP 距离。

**一个精妙的点**：为什么修正值取"当前较长根"而不是"历史平均值"？
因为断掉的那根只会变短、不会变长，长的那根是可信的真实高度；
而且它是**当前帧实测值**，车忽远忽近的透视变化它自己就带着，不会像历史固定值那样过时。

## 三、全视频 A/B 实测数据（1770 帧）

| 指标 | 结果 | 说明 |
|---|---|---|
| 框数变化帧数 | **0** | 没有多框/少框 |
| 中心位移帧数 | **0** | 框的位置纹丝不动 |
| 变成 invalid 的板 | **0** | 没有引入坏框 |
| 被修正的板 | 72 处 | 全是远处断灯条板 |
| 被修板 ratio 范围 | 0.55~0.72 | 全在目标区间内 |
| 被修板 hMax 范围 | 35~44px | 全是远处小板 |
| 被修板位置 | 中心 x≈412~432 | 全是画面左侧那辆车 |

被修的 72 处集中在帧 165~178、880~888、1597~1607 三段——
都是车在左侧远处、灯条断成两截的时候，和 157 帧是同一类问题。

**距离为什么变化大（至 0.94m）？** 这是修正本身的效果，不是误伤：
原来框高被短截压到 ~32px，PnP 算出偏大的距离；修正到 ~41px 后距离更接近真实。
肉眼看 f171：4.11m→3.56m、f886：4.19m→3.21m，框都变正、贴合灯条了。

## 四、怎么启用（默认关闭，效果确认后再开）

滤波器默认 `enabled=false`，不加参数时行为和以前**完全一样**。启用方式二选一：

- **命令行**：`armor_vision.exe --mode video --temporal ...`
- **CLion**：Run/Debug Configurations → Program arguments 里加 `--temporal`

启动时若看到 `[temporal] 时序多数投票已启用` 就说明生效了。

想调判据松紧，改 `TemporalFilter.h` 里 `TemporalParam` 的默认值即可：
- `persistLow / persistHigh`：ratio 判定区间；
- `persistHMax`：灯条像素高度上限（挡近处大板）；
- `stabilityMax`：历史波动上限（越小越保守）。
