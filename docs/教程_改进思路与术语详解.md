# 改进思路与术语详解（教程）

> 这份文档解释三件事：**这条流水线是怎么一步步改进出来的**、**每一步为什么这么改**、
> **里面所有专业名词到底是什么意思**。
>
> 读法建议：先看第 1 节了解全貌，再看第 3 节的改进历程（那是核心），

## 1. 这个项目在干什么

### 一句话

**把"图像上一块发光的东西"，变成"空间里一个精确的三维坐标"。**

### 完整流水线（7 步）

```
一帧 1440×1080 的 BGR 图像
   │
   ├─① 灯条检测      light_bar_detector.cpp
   │     颜色通道差 → 二值化 → 形态学 → 找轮廓 → 几何筛选 → PCA 定方向
   │     产出：0~15 根"灯条"（每根有中心、长度、宽度、方向、亮度）
   │
   ├─② 灯条配对      armor_matcher.cpp
   │     两两组合 + 五条几何约束 + 打分 → 挑出"最像一块装甲板"的组合
   │
   ├─③ 角点外推      armor_corners.cpp
   │     用两根灯条的轴线做直线求交，得到装甲板四个理论角点
   │
   ├─④ 亚像素精化    armor_corners.cpp
   │     cornerSubPix 把角点从整像素细化到 0.1 px 量级
   │
   ├─⑤ 位姿估计      pnp_solver.cpp
   │     4 个像素点 + 已知尺寸 + 内参 → 相机坐标系下的位置和姿态
   │
   ├─⑥ 时序确认      temporal_filter.hpp
   │     连续 3 帧一致才算真目标；短暂丢失用预测续上
   │
   └─⑦ 绘制输出      visualizer.cpp + main.cpp
         画框、画角点、画中心、写坐标和耗时、写 CSV
```

### 一句话说清每步在解决什么

| 步骤 | 解决的问题 | 如果这步做得不好会怎样 |
|---|---|---|
| ① 灯条检测 | 从黑暗背景里把 LED 灯条抠出来 | 灯条碎了 → 配不成对 → 漏检 |
| ② 配对 | 判断"这两根灯条是不是同一块装甲板的左右两条" | 配错 → 把背景当成装甲板 |
| ③ 角点外推 | 把"灯条端点"变成"装甲板的四个角" | 角点抖 → 位置抖 |
| ④ 亚像素 | 把角点精度从 1 px 提到 0.1 px | 距离误差大 10 倍 |
| ⑤ PnP | 从 2D 像素反推 3D 位置 | 坐标错，或姿态不可信 |
| ⑥ 时序 | 用时间维度过滤单帧的偶然错误 | 画面乱闪、目标甩丢 |
| ⑦ 输出 | 把结果给人看 | 无从判断对错 |

## 2. 专业名词详解

### 2.1 图像与颜色

| 名词 | 大白话解释 | 本项目用在哪 |
|---|---|---|
| **BGR** | OpenCV 存彩色的顺序：蓝、绿、红三个通道。注意和常见 RGB 反着来 | `cv::split` 出来的 `ch[0]=B, ch[1]=G, ch[2]=R` |
| **通道（channel）** | 一张彩色图其实是三张灰度图叠在一起，每张就是一个通道 | 通道差、亮度门限都要分别取通道 |
| **通道差** | 两个通道相减，比如 `R − B`。用来突出"某个颜色比另一个颜色强"的区域 | 让白色背景灯消失、只留橙红 LED |
| **饱和度** | 颜色有多"纯"。纯红饱和度高，粉色低 | 解释为什么白色灯在 R−B 下是 0 |
| **过曝 / 饱和** | 像素亮度达到上限 255，再亮也是 255，信息丢失 | 灯条中心过曝导致 R−G 失效 |
| **灰度图** | 只有一个亮度值的图（0 黑 ~ 255 白） | 亚像素精化要用单通道图 |
| **HSV** | 另一种描述颜色的方式：色相 H、饱和度 S、亮度 V | 我们**没用**它，理由见 §3.2 |

### 2.2 二值化与形态学

| 名词 | 大白话解释 | 本项目用在哪 |
|---|---|---|
| **阈值（threshold）** | 一条分界线：大于它算白，小于它算黑 | `diff_threshold: 85` |
| **二值化** | 把灰度图变成只有黑白的图 | 阈值化的那一步 |
| **Otsu 法** | 一种"自动找阈值"的算法，假设图里有明显的两类（前景/背景） | 我们**不用**，理由见 §3.2 |
| **形态学** | 一组基于"小窗口滑动"的图像操作，用来修整黑白区域的形状 | 去噪、补断 |
| **核（kernel）** | 那个"滑动的小窗口"，尺寸写作 `宽×高`，如 3×3、3×17 | `morph_open_kernel: 3`、`morph_close_h: 23` |
| **腐蚀（erode）** | 让白色区域**瘦一圈**：3×3 的核里 9 个像素全白才保留中心 | 去掉小噪点 |
| **膨胀（dilate）** | 让白色区域**胖一圈**：核里有任意一个白就变白 | 填补缝隙 |
| **开运算（open）** | 先腐蚀再膨胀 = 大小不变、去掉孤立小点 | 去掉 JPEG 噪点 |
| **闭运算（close）** | 先膨胀再腐蚀 = 大小不变、补上内部缝隙 | **补灯条的竖向断裂** |
| **连通域 / 连通块** | 一片连在一起的白色像素 | 一根灯条就是一个连通块 |

### 2.3 轮廓与几何

| 名词 | 大白话解释 | 本项目用在哪 |
|---|---|---|
| **轮廓（contour）** | 一个白色区域的边界线，是一串点的坐标 | `cv::findContours` |
| **`CHAIN_APPROX_NONE`** | 求轮廓时保留边界上**每一个**像素点 | 我们**改成了**下面的 SIMPLE |
| **`CHAIN_APPROX_SIMPLE`** | 求轮廓时把直线段压缩成端点，只留"拐角" | 减少点数、避免 PCA 被带偏 |
| **`minAreaRect`** | 能**旋转**的最小外接矩形，返回 中心、宽高、角度 | 量灯条的尺寸 |
| **长宽比（aspect ratio）** | 长度 ÷ 宽度。灯条约 4~5，圆形光斑约 1 | 区分灯条和光斑 |
| **填充率（fill ratio）** | 轮廓面积 ÷ 外接矩形面积。实心矩形≈0.95，圆形≈0.785 | 剔除不规则形状 |
| **PCA / 主成分分析** | 找一堆点的"最长延伸方向"。这里等价于"灯条的朝向" | 用 `cv::fitLine` 实现 |
| **`fitLine`** | OpenCV 的最小二乘直线拟合，输出方向向量 | 比 `minAreaRect` 的角度稳定 |
| **单位向量** | 长度为 1 的方向向量，只表示方向不表示大小 | `axis`、`half` 字段 |
| **投影（projection）** | 把一个点投到某个方向上，得到它在该方向的坐标 | 求灯条的真实长度/宽度 |
| **亚像素（sub-pixel）** | 精度比一个像素更细，比如 0.3 px | `cornerSubPix` |
| **`cornerSubPix`** | OpenCV 的角点细化算法：在角点周围的小窗口里找灰度重心，把位置精确到亚像素 | 把重投影误差从 1.0 px 降到 0.44 px |
| **凸四边形 / 自交** | 四个角按顺序连起来不交叉 | 验证角点顺序正确 |

### 2.4 相机与位姿

| 名词 | 大白话解释 | 本项目用在哪 |
|---|---|---|
| **针孔模型** | 把相机想成一个点 + 一块成像平面，`u = fx·X/Z + cx` | 所有几何的基础 |
| **内参（intrinsics）** | 描述相机自身特性的四个数：焦距 fx/fy、主点 cx/cy | `calibration.yaml` 里的 `camera_matrix` |
| **fx / fy** | 用"像素"表示的焦距：1 米处 1 米宽的物体占多少像素 | fx=2334 → 8 mm 镜头 / 3.45 µm 像元 |
| **主点 cx / cy** | 光轴打在图像上的位置，理想是图像中心 | cx=722.6（不是 720，说明标定是真做的） |
| **畸变（distortion）** | 镜头不完美导致直线拍成弯的。径向畸变 k1/k2/k3，切向 p1/p2 | k1=−0.08 是桶形畸变 |
| **去畸变** | 按畸变模型把像素"掰回"正确位置 | `cv::undistortPoints` |
| **外参（extrinsics）** | 两个坐标系之间的旋转和平移 | `R_camera2gimbal`、`t_camera2gimbal`（手眼标定） |
| **PnP** | Perspective-n-Point：已知 n 个 3D 点 + 它们的 2D 像素，求相机位姿 | 核心的位姿解算 |
| **IPPE** | 一种专用于**共面**点的 PnP 解析解法（无需初值） | `SOLVEPNP_IPPE` |
| **重投影误差** | 用解出来的位姿把 3D 点投回图像，和实际像素比距离 | 既用来消歧，也用来判断可信度 |
| **镜像解 / 平面歧义** | 平面目标存在"翻转 180°"的孪生解，投影几乎一样 | IPPE 返回 2 组解，用重投影误差选 |
| **rvec / tvec** | 旋转向量（3 个数表示旋转）、平移向量（3 个数表示位置） | PnP 的输出 |
| **LM（Levenberg-Marquardt）** | 一种迭代优化算法，用来最小化重投影误差 | `solvePnPRefineLM` 精化 |
| **自由度 / 可观性** | 6 个未知数里，哪些能被数据可靠地算出来 | 位置和 yaw 可观，**pitch 不可观** |
| **深度-俯仰耦合** | 板子后仰会让投影变矮，而"离得更远"也让投影变矮，两者无法区分 | 这就是 pitch 不可观的原因 |
| **单应（homography）** | 平面到平面的 3×3 投影变换，8 个自由度 | `warpPerspective` 把歪的板子拉正 |
| **透视投影** | 近大远小，平行线会汇聚 | 四边形宽高比会随视角变化 |

### 2.5 滤波与跟踪

| 名词 | 大白话解释 | 本项目用在哪 |
|---|---|---|
| **卡尔曼滤波** | 用"预测 + 观测"加权来估计状态，同时给出速度 | `tracker.cpp`，6 状态 [x y z vx vy vz] |
| **Q（过程噪声）** | 我有多不相信"匀速"这个假设。Q 大→更贴观测→响应快但抖 | `tracker_process_noise: 0.001` |
| **R（测量噪声）** | 我有多不相信测量值。R 大→更信预测→平滑但滞后 | `tracker_measure_noise: 0.01` |
| **状态机** | 用有限的几个状态 + 转移条件来描述逻辑 | 时序层的 4 个状态 |
| **时序一致性** | 真目标相邻帧位置连续、速度有限；假目标忽有忽无 | 时序确认层的核心思想 |
| **ROI（region of interest）** | 只处理图像的一小块区域，而不是整幅 | `--roi`，把 detect 从 7.5 ms 降到 0.7 ms |
| **续帧（predicted）** | 本帧检测失败，用上一帧的预测位置顶上 | `confirm_max_misses: 5` |

## 3. 改进历程（五轮迭代）

每一轮都是：**发现现象 → 定位根因 → 改一处 → 实测验证**。
所有数据都来自同一段视频（A 段 `462305`，1440×1080）。

### 总览

| 版本 | 改了什么 | 检出率 | 位姿有效率 | 重投影误差 |
|---|---|---|---|---|
| v1 | 初版：`CHAIN_APPROX_NONE`、闭运算 3×17、角点取灯条端点 | 74.5% | 71.5% | 0.91 px |
| v2 | 轮廓改 `CHAIN_APPROX_SIMPLE` | 78.5% | 75.5% | 1.07 px |
| v3 | 闭运算核高度 17 → 23 | **88.5%** | 85.5% | ~1.0 px |
| v4 | 角点改直线求交 + `cornerSubPix` | 88.0% | **87.0%** | **0.441 px** |
| 全量 | v5 稳定版（含门限与显示分离） | 84.2% | 83.8% | 0.442 px |

> 注：v1~v4 是"前 200 帧"的对比数据，最后一行是全 1770 帧，两者不能直接比。
> 同一段数据里，"前 200 帧"比全量更容易漏（目标更远），所以数字偏低是正常的。

---

### 第一轮：轮廓点数把尺寸量偏了

**现象**：检出率只有 74.5%，远低于预期。

**根因**：`cv::findContours` 用了 `CHAIN_APPROX_NONE`，它返回边界上**每一个**像素点。
一条 70×13 的灯条会返回约 166 个点（而不是 4~8 个拐角点）。这带来两个后果：

1. **宽度被撑大约 1 px**。我们用"把轮廓点投影到轴上取 min/max"来量长宽，所有边界点都在里面，
   宽度比真实值大 1 px。对一条 13 px 宽的灯条，1 px 就是 **8% 的误差** ——
   长宽比从 3.9 掉到 3.6，接近下限（1.5）的窄灯条直接被筛掉。
2. **PCA 主轴被像素阶梯带偏**。轮廓点全部落在锯齿状的边界上，拟合出的方向有几度误差，
   而配对要求两根灯条角度差 ≤10°，几度就足以误杀。

**改动**：`CHAIN_APPROX_NONE` → `CHAIN_APPROX_SIMPLE`（只保留拐角点）。

**效果**：74.5% → 78.5%（+4 个点）。

**为什么 SIMPLE 更好**：几何拟合（直线、矩形、方向）关心的是**形状**，不是**边界像素的密度**。
`SIMPLE` 保留了所有拐角信息，去掉的全是冗余的直线段中间点。

**怎么定位的**：用 Python 复刻同一套算法，只切这一个参数：
`SIMPLE` 得 85.0%、`NONE` 得 75.0% —— 和 C++ 的 78.5% 对得上，确认是这个因素。
这叫**消融实验（ablation）**：一次只改一个变量。

---

### 第二轮：灯条被切成两段

**现象**：还有一批帧完全检不到，且集中在目标较远的时候。

**根因**：把失败帧的所有轮廓打印出来看，发现有根灯条被切成了**两段**：

```
本来是一根 70 px 的灯条，被切成了 40 px + 25 px 两段
→ 两段各自的长宽比都不对，或者长度比超过 1.25，配不成对
```

为什么会断？三个原因叠加：
1. **JPEG 压缩的 8×8 块效应**，窄处会出现暗块
2. **数字遮挡**（灯条和数字重叠的部分被压暗）
3. **LED 灯珠本身有间隙**

**改动**：闭运算的核从 3×17 加高到 **3×23**。

**为什么是"竖长条"而不是方形核**：灯条是**竖直**细条，它的断裂必然是**竖向**的。
竖核能补竖向缺口，但不会把**左右相邻**的两根灯条粘成一块 —— 而 17×17 的方核会。

**为什么是 23**：扫出来的。

| 核高 | 检出率 |
|---|---|
| 9 | 59% |
| 13 | 59% |
| 17 | 78.5% |
| **21** | **87.5%** |
| **23** | **88.5%** |
| 25 | 88.5%（饱和） |

**效果**：78.5% → 88.5%（+10 个点），是整个改进里收益最大的一步。

**这里的方法论**：参数不是"看着调"的，是**扫出来的**。而且要看**曲线形状**：
从 21 开始饱和，说明"缺口都补上了"，再加大没有意义。

---

### 第三轮：角点从"端点"改成"直线求交"

**现象**：检出率够了，但**重投影误差**有 1.0 px 左右，位置在抖。

**根因**：原来的四个角点是**四次独立测量** —— 直接取两根灯条的端点。
任何一次抖动（灯条末端被遮挡、JPEG 把边缘压断、少亮一颗灯珠）都会原封不动进入 PnP。

**改动**：换成"直线约束"的构造：

```
每根灯条：
  u     = 中心轴线方向（PCA 拟合）
  n     = 外法线（垂直 u，指向远离另一根灯条的方向）
  外缘线 = 过 (中心 + n × 半宽)、方向 u 的直线

上下边界线：
  过两根灯条的"外缘顶点"，方向 = 垂直（两根灯条方向的平均值）

四个角点 = 左右两条外缘线 × 上下两条边界线的交点
```

**为什么这样更稳**：每个角点被**两条完整的直线**约束，而不是被一个噪声点决定。
一根灯条端点抖了，只是让那条边界线稍微转了一点，四个角点会**一起**平滑地动，而不是各自乱跳。

**两个刻意的设计选择**：

1. **左右两条边各用自己的灯条方向，不强制平行**。
   如果强行平行，四边形就成了平行四边形，而真实透视下矩形会呈现为一般四边形（近大远小，两边收敛）。
   强加平行会引入系统偏差。

2. **上下边界线的方向用"两根灯条方向的平均值"的垂线**。
   上下边必须垂直于灯条（矩形这一物理事实），用平均值可以把两根灯条各自的几度角度噪声**平均掉一半**。

**再加一步亚像素精化**：`cornerSubPix` 在灯条的高对比边界上找灰度重心，
把角点从"整像素"细化到 0.1 px 量级。

**效果**：重投影误差 **1.0 px → 0.441 px**（降了 56%），位姿有效率 85.5% → 87.0%。

---

### 第四轮：为了"框好看"牺牲了精度（这是我犯的错）

**现象**：为了让绿框看起来"贴着灯条内侧、包住数字"，我把
`plate_edge_offset` 设成了 **−1**（边线取灯条内缘）。

**后果**：检出率 88.0% → **81.6%**，重投影误差 0.441 → **0.755 px**。

**根因**：我把"物理测量"和"画面显示"混在**同一个参数**上了。

- 物理事实：135 mm 是**灯条外缘到外缘**的距离
- 用内缘去算 PnP，等于告诉它"这块板只有 120 mm 宽"，但实际是 135 mm
- 结果：**系统性失配** → 重投影误差上涨；同时框变窄 → 宽高比掉到 1.9 → 部分帧被 `min_quad_aspect` 卡掉

**改动**：彻底拆开两个概念：

| 参数 | 管什么 | 现值 | 影响精度 |
|---|---|---|---|
| `plate_edge_offset` | **PnP 用的角点**（物理） | **+1.0**（外缘） | ✅ 正确 |
| `draw_inset_ratio` | **只影响画面**：左右边内收 9% | 0.09 | ❌ 不影响 |
| `draw_extra_height_ratio` | **只影响画面**：上下加高 90% | 0.9 | ❌ 不影响 |
| `draw_inflate_px` | **只影响画面**：整体外扩 5 px | 5.0 | ❌ 不影响 |

**效果**：精度回到 0.442 px，检出率回到 84.2%，而框的样子仍然是你要的样子。

**教训（很重要）**：

> **"测量的起点"和"显示的样式"必须是两个独立的量。**
> 一旦它们共用一个参数，就会出现"改画面把数据改坏"的连锁反应。

---

### 第五轮：背景误检的量化与治理

**现象**：背景灯具偶尔凑成一块装甲板，画面上闪一个框。

**做法**：先用数据量化，再决定加什么约束。

统计 500 帧，把"真目标（距离 < 3.5 m）"和"疑背景（距离 ≥ 3.5 m）"两类样本的
两个候选特征拉出来比：

| 特征 | 真装甲板 | 疑背景 | 分离度 |
|---|---|---|---|
| **像素尺寸** | min 55.6 / p50 65.5 / max 81.1 | max 23.2 / p50 15.2 | **完美**（空档 23→56） |
| 亮度比 | p50 1.01 / p95 **1.47** / max 2.28 | p50 1.05 / p95 **1.11** / max 1.18 | **反向**（背景更一致！） |

**结论**：

- **像素尺寸可用**：45 px 落在空档里 → 挡掉 **268/268** 背景，误杀 **0/423** 真目标
- **亮度比不可用**：挡掉 0/268 背景，却误杀 67~120/423 真目标 → **关掉**

**我犯的错**：亮度比这个约束是我**凭物理直觉先加的**（"同一块板的两根灯条由同一路 LED 驱动，亮度应该接近"）。
听起来很合理，但**实测背景灯具的亮度反而更一致**，这个特征完全没有区分度。
而我先加约束、后验证，导致检出率掉了 12.5 个点。

**教训**：

> **先量分布，再定阈值。**
> 判断一个特征能不能用，标准不是"它在物理上是否合理"，而是
> **"两类样本的分布有没有重叠"**。
> 有重叠 → 收紧就误杀、放松就没用，不能当硬阈值；
> 有空档 → 阈值放在空档中间，两边都不碰，非常可靠。

**最终效果**：1483 个有效位姿帧里，只有 **4 帧**距离超过 3.5 m（0.27%），最远 7.10 m。

## 4. 九个真实 bug 案例（每个都有教育意义）

### 案例 1：`CHAIN_APPROX_NONE`（已在上文）

**教训**：几何拟合类算法，默认用 `CHAIN_APPROX_SIMPLE`。
`NONE` 只在需要逐像素形态（算周长、轮廓匹配）时才用。

### 案例 2：`getTextSize` 的返回值读错了

**现象**：面板上四行字**全叠在一起**，黑底也窄成一条线。

**根因**：

```cpp
// 错：把第 5 个参数（baseline 输出）当成了文字高度，返回值直接丢掉
cv::getTextSize(s, FONT_HERSHEY_SIMPLEX, scale, thickness, &bh);
return cv::Size(bw, bh);   // bw 永远是 0，bh 是基线（约 11），不是高度（约 21）
```

后果连锁：行距算成 `11×1.8=20 < 字高 21` → 叠字；面板宽度算成 `0+padding` → 黑底缩成一条。

**正确写法**：

```cpp
int baseline = 0;
return cv::getTextSize(s, FONT_HERSHEY_SIMPLEX, scale, thickness, &baseline);
```

**教训**：OpenCV 里这类"返回值 vs 输出参数"的坑很多：

| 函数 | 坑 |
|---|---|
| `cv::getTextSize` | **返回值**是尺寸，第 5 个参数是 baseline |
| `cv::threshold` | 返回值是实际用的阈值，图像在输出参数里 |
| `cv::minMaxLoc` | 结果全走输出参数，无返回值 |
| `cv::solvePnPGeneric` | 返回解的数量，解在 vector 里 |

**而且这类错编译器不会管**，只能靠"跑起来看一眼"发现。

### 案例 3：YAML 文件被写进了 BOM

**现象**：程序启动直接报 `config/default.yaml(1): Invalid or unsupported syntax`。

**根因**：Windows PowerShell 的 `Set-Content -Encoding UTF8` 会自动在文件头加
**BOM（Byte Order Mark，EF BB BF 三个字节）**。OpenCV 的 YAML 解析器不认它，
所以"第 1 行语法错误" —— 而第 1 行 `%YAML:1.0` 本身完全合法。

**教训**：
- **看到"第 1 行非法"而第 1 行看起来正常，第一反应查 BOM**
- 在 Windows 上写 UTF-8 文件要用：`[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($false)))`
- **在 Ubuntu 里用 `sed -i` 改文件不会有这个问题**（这个坑只存在于 Windows 侧编辑）

### 案例 4：CSV 表头和数据列数不一致

**现象**：对比脚本算出来的 `pose% = 0.0`、`err = nan`、`bars/f = 0.83`，全是错位值。

**根因**：表头写了 15 列，但数据行只写了 14 列 —— **漏写了 `pnp_ms`**。
于是 `csv.DictReader` 按列名取值时，从第 5 列开始**整体错位一格**：
`n_armors` 那一列读到的其实是 `pose_ok`。

**教训**：
- 写 CSV 时，**表头和写入语句要写在相邻的位置**，中间别隔几百行
- 更稳的做法：写完之后 `head -3` 看一眼，数一下逗号
- 这类错不会报错，只会让后续统计全部失真

### 案例 5：宽高比检查放在了板高外扩之后

**现象**：把 `armor_height_m` 从 0.056 改成 0.11（让框包住数字）之后，**什么都检不出来了**。

**根因**：`aspect`（宽高比 1.4~3.2）是用来判断"两根灯条是不是同一块板"的，
它应该看**灯条本身**的几何（135:56 = 2.41）。但我把"板高外扩"放在它**前面**，
板子一变高，宽高比掉到 1.3 → 被过滤器直接丢掉。

**改动**：把 `aspect` 的计算移到外扩**之前**。

**教训**：**每个判据要知道自己在判断什么物理事实**。
宽高比判断的是"两根灯条的关系"，所以必须在"板子变形"之前算。

### 案例 6：亮度比这个特征没有区分度（已在上文）

### 案例 7：时序层的"播种"被漏掉了

**现象**：时序状态分布里 **confirmed 永远是 0**，所有帧都是 tentative。

**根因**：状态机第一次遇到候选时，`has_target_ == false`，于是跳过了关联循环、
走进了"关联失败"分支，而失败分支最后调 `reset()` ——
**把挑战者计数也清零了**，所以计数器永远停在 1，到不了 3。

**改动**：加入"播种"分支：

```cpp
if (!has_target_) {
  if (cands.empty()) { state = kNone; return -1; }
  has_target_ = true;
  hits_ = 1;              // ← 从 1 开始累计
  remember(cands.front());
  state = (hits_ >= confirm_hits) ? kConfirmed : kTentative;
  return 0;
}
```

**教训**：**状态机一定要检查"初始状态"的转移**。
我在重写时把老版本的播种逻辑漏掉了，而这类 bug **不会报错、不会崩**，
只会让功能静默失效 —— 所以必须**用统计/日志验证功能真的生效了**。

### 案例 8：`primary_override = -1` 的语义冲突

**现象**：时序层判定"续帧期没有主目标"，但画面上还是画了一个框。

**根因**：我用 `-1` 表示"时序层没选"，而 `primaryIndex()` 里 `-1` 的语义是
"没设过，按 score 取"。于是它回退到单帧最高分，把未确认的候选又画成了主目标。

**改动**：用 `-2` 表示"时序层明确判定没有主目标"，和 `-1`（没设过）区分开。

**教训**：**哨兵值（sentinel value）的语义要唯一**。
一个变量同时表示"没设置"和"设置为空"，必然出问题。

### 案例 9：ROI 窗口在丢帧时"冻结"

**现象**：只开 `--roi` 不开 `--tracker` 时，目标一走就丢 —— 窗口停在原地不动。

**根因**：`predictOnly()` 只在 `enable_tracker` 时调用。
但 ROI 窗口是靠**预测位置**定位的，不推进滤波器，窗口就永远停在上次的位置。

**改动**：

```cpp
if (cfg.detector.enable_tracker || cfg.detector.enable_roi) tracker.predictOnly();
```

另外加了两条自愈机制：
- 丢失期间窗口每次 **×1.6**（上限 600 px），跟错窗不会立刻整段丢失
- 窗口里配不出装甲板 → **当场退回全图重试一次**（代价只付在本来就会漏的帧上）

**教训**：**功能之间的隐式依赖要想清楚**。
ROI 依赖预测，预测依赖滤波器推进 —— 少这一行，ROI 就半残。

## 5. 几个关键设计决策（答辩常问）

### 5.1 为什么用 `R − B` 而不是 `R − G` 或 HSV

这段素材是 **2 ms 曝光**、整体极暗。实测同一帧：

| 通道 | 灯条像素 | 形态 |
|---|---|---|
| `R − G` | 348 px | **碎成 5 块**（绿通道被过曝抬高） |
| `R − B` | 1882 px | **两块完整**（523 / 496 px） |

原理：灯条中心已经过曝，绿色通道被抬高，所以 `R−G` 变小；而蓝色通道始终很低，`R−B` 稳定。
白色背景灯 `R≈G≈B`，任何通道差都趋近 0 → 顺带解决背景。

**不用 HSV 的原因**：H 是比值函数（分母 `max−min`），暗处和过曝处都不稳定；
而且红色跨 H 的 0/179 边界，要拆成两个区间。

### 5.2 为什么闭运算用竖长条核

灯条是竖直细条，**断裂必然是竖向的**。竖核能补竖向缺口，但不会把左右相邻两根灯条粘成一块。
方核会把它们粘在一起 —— 那就从"漏检"变成"错检"，更糟。

### 5.3 为什么四角点取"灯条外缘"而不是中心线

题目给 135 mm 是装甲板**总宽**（外缘到外缘），56 mm 是灯条长度。
用外缘四角，物体点严格是 `(±67.5, ±28, 0)` mm。
如果用灯条中心线，横向会有约一个灯条宽度（12 mm）的系统误差 → 距离误差 9%。

### 5.4 为什么 ROI 能快 10 倍

```
全图  1440×1080 = 1,555,200 像素
窗口   400×400  =   160,000 像素   → 1/9.7 的计算量
```

实测 `detect` 7.51 ms → 0.72 ms（−90%）。
但**端到端 FPS 只从 73 涨到 130**，因为 MJPG 解码固定占 6 ms 左右，省不掉。

### 5.5 为什么卡尔曼在 166 fps 下收益小

帧间隔只有 6 ms，目标在 6 ms 内几乎不动，"平滑"没有东西可平滑。
它的真正价值是**延迟补偿**：从曝光到算出结果有十几毫秒，那时目标已经移动了，
需要把位姿**外推到击发时刻**。

### 5.6 为什么 6 个自由度里 pitch 不可靠

```
4 个共面点 → 8 个方程 → 解 6 个未知数（超定）
但"超定"不等于"每个自由度都准"
```

| 自由度 | 依赖的像素量 | 像素长度 | 1 px 误差 → |
|---|---|---|---|
| 距离 z | 板**宽** | 178 px | 1.0 cm |
| yaw | 板宽随 cos 收缩 | 178 px | 0.3° |
| **pitch** | 板**高** | **68 px** | **10°** |

**机制**：pitch 让板"变矮"（`56·cos θ`），而"离得更远"也让板"变矮" ——
两者在图像上完全等价，这叫**深度-俯仰耦合**。板高只有 68 px，杠杆太小。

**实测佐证**：pitch 标准差 15.9°（A 段）/ 25.1°（B 段），相邻帧符号翻转 300~500 次，
而同期重投影误差只有 0.44 px —— **拟合完美但那个自由度是噪声**。

**结论**：叠加层只显示 yaw，不显示 pitch。CSV 里保留 `pitch_deg` 列供分析，但不作为控制量。

## 6. 指标怎么读

| 指标 | 大白话 | 你的值 |
|---|---|---|
| `frames with armor` | **检出率**：有目标时你找到了几成 | 84.2% |
| `valid pose` | 找到后，位置算得可信的占比 | 83.8% |
| `confirmed target` | 通过时序确认的占比 | 80.2% |
| `interference` | 场景有多脏：候选灯条 → 候选配对 → 最终通过 | 9.7 → 44.2 → 0.88 |
| `roi window` | 用窗口搜索的帧占比（提速来源） | 87.8% |
| `detect median` | 找灯条耗时 | 0.72 ms（ROI）/ 7.51 ms（全图） |
| `total median` | 一帧总共（**含解码**） | 6.15 ms |
| `end-to-end` | 实际每秒处理帧数 | 130.6（ROI）/ 73.3（全图） |
| `median range` | 算出的距离中位数 | 1.92 m |

```
detect      只算找灯条            ← 炒菜时间

end-to-end  整个程序每秒多少帧     ← 还含启动、写文件
```

## 7. 答辩问答（20 题）

**Q1：四个角点对应哪四个物理点？**
灯条**外缘**的四个角。135 mm 是两条灯条外缘之间的距离，56 mm 是灯条长度，
所以物体点是 `(±67.5, ±28, 0)` mm。**这题答错，后面全废。**

**Q2：为什么用 R−B 不用灰度？**
白灯管灰度能到 240，和灯条一样亮，灰度分不开；`R−B` 让白灯管归 0、灯条保留。

**Q3：Otsu 为什么不能用？**
2 ms 曝光下 99% 像素挤在 0 附近，直方图不是双峰，Otsu 会把阈值压到 10 量级 → 全图变前景。

**Q4：IPPE 为什么返回两组解？**
平面目标存在"翻转 180°"的镜像解，投影几乎一样。用**重投影误差小的** + 要求 `tvec.z > 0` 来筛。

**Q5：你的距离误差多大？**
角点 1 px 误差在 2 m 处 ≈ 1.27 cm（`δd/d = δw/w`，板宽 158 px）。
用了亚像素后中位重投影误差 0.44 px。

**Q6：怎么在没有真值的情况下验证？**
双路径自洽：PnP 的 `z` vs `fx×0.135/板宽像素`，B#400 帧是 2.531 vs 2.530 m。

**Q7：为什么 pitch 不显示？**
4 点共面 PnP 里 pitch 和深度耦合，板高只有 68 px，1 px 误差对应 10° pitch。
实测标准差 15.9°，是噪声。

**Q8：166 fps 下卡尔曼有什么用？**
平滑收益接近零（6 ms 内目标不动）。价值是**延迟补偿**：把位姿外推到击发时刻。

**Q9：ROI 能提速多少？为什么端到端只涨 1.8 倍？**
`detect` 从 7.51 → 0.72 ms（−90%），但解码固定占 6 ms，所以端到端 73 → 130 FPS。

**Q10：ROI 会不会因为跟错窗丢目标？**
有三层保护：丢失时窗口每次放大 1.6 倍；超过 `roi_lost_frames` 回退全图；
窗口里配不成对就**当场全图重试**。实测回退 214 次、重试 107 次。

**Q11：怎么防止背景误检？**
五层过滤：形态（长宽比/填充率/倾角）→ 组合（长度比/平行度/间距比/宽高比）
→ 统计（score ≤ 1.2）→ **尺寸**（像素宽度 ≥ 45 px）→ **时序**（连续 3 帧）。

**Q12：为什么用"像素宽度"而不是直接卡距离？**
`w = fx×0.135/d`，宽度和距离一一对应，但**在 PnP 之前就能算**，省一次解算。
45 px 等价于 7.0 m。

**Q13：那个亮度比约束为什么关掉了？**
实测无区分度：真目标 p95=1.47、背景 p95=1.11（背景反而更一致）。
收紧到 1.35 只误杀 16% 真目标，挡不住任何背景。

**Q14：时序确认有什么用？**
挡住"只出现一两帧"的候选；已确认目标短时丢失时用预测续帧（实测 8.6% 的帧是续帧）。

**Q15：新目标出现会被抑制多久？**
`confirm_hits: 3` 帧 = 18 ms。另外有"快速切换通道"：新目标连续 3 帧就切换，不会被旧目标锁死。

**Q16：为什么中心点不喂给 PnP？**
1 个点 + 已知尺寸无法反解 6 个自由度。中心点只用于显示和跟踪。

**Q17：为什么用 IPPE 而不是深度学习？**
位姿估计的输入是 4 个角点，问题已退化成几何问题，解析解是像素级最优的。
深度学习在这里只会引入不可解释的误差。

**Q18：为什么不用 YOLO？**
三个理由：无标注；公开权重是正常曝光域（这份数据是 2 ms 极暗）；灯条是自发光饱和目标，
颜色分割近乎二值可分，正是传统方法的主场。

**Q19：你的系统还有什么局限？**
pitch 不可观；大角度侧对时投影宽度收缩会被尺寸门限卡掉；跨板配对在几何上仍可能成立。

## 9. 一句话总结这段工程

> 这个项目的本质是**把一个 3D 问题拆成一系列可独立验证的 2D 子问题**：
> 先证明灯条找对了，再证明配对对了，再证明角点准了，最后才敢相信 PnP 输出的坐标。
>
> 每一步都用**可量化的指标**做验收（检出率、重投影误差、状态分布），
> 而不是"看着差不多"。
>
> 而所有阈值的确定方法都是同一个：**先量分布，再找空档，把阈值放在空档里**。
> 没有空档的特征（比如亮度比），无论听起来多合理，都不能用。
