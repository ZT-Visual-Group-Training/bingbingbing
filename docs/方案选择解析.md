## 0. 总路线：传统视觉 vs 深度学习

| 方案 | 优点 | 缺点 | 在本数据上 |
|---|---|---|---|
| **深度学习（YOLO 检测 + PnP）** | 复杂背景鲁棒、端到端 | 需标注；域差异敏感；黑盒难解释 | ❌ 不可行 |
| **传统视觉（颜色分割 + 几何约束）** | 无需标注；可解释；CPU 实时 | 依赖阈值；强光/过曝敏感 | ✅ 可行 |
| **混合（传统做检测，学习做分类）** | 兼顾 | 复杂度翻倍 | 本次不需要 |

**选传统视觉，三个理由**：

1. **本数据零标注** —— 考核只给了视频，没有框标注，训练不了检测器
2. **域差异极大** —— 公开权重是正常曝光域，这份数据是 **2 ms 极暗**，灯条中心过曝
3. **灯条是自发光饱和目标** —— `R−B` 分割后近乎二值可分，**这正是传统方法的主场**

**代价**：所有阈值都要在数据上标定，换场景要重调。

**什么时候该换**：如果背景里有大量**非自发光**的橙色物体（队员衣服、场地道具），颜色分割会失效，
那时需要学习型检测。

**架构留了接口**：检测层是独立模块（`light_bar_detector`），将来有标注可以直接替换。

## 1. 颜色通道：灰度 / HSV / R−G / R−B / YCrCb

| 方案 | 原理 | 在本数据上的实测 |
|---|---|---|
| 灰度 | 亮度阈值 | ❌ 白灯管 240、灯条 250 —— 分不开 |
| **HSV** | 色相/饱和度/亮度 | ⚠️ 暗处不稳定；红色跨 H 的 0/179 边界 |
| `R − G`（社区常用） | 红灯比绿灯强 | ❌ **348 px，碎成 5 块** |
| **`R − B`（采用）** | 红灯比蓝灯强 | ✅ **1882 px，两块完整（523 / 496）** |
| YCrCb 的 Cr | 归一化色度 | ⚠️ 与 `R−B` 接近，无额外收益 |

**为什么 `R−G` 会失效**：

灯条中心已经**过曝**（亮度到 255），绿色通道被一起抬高了。
```
中心：(255, 190, 40) → R−G = 65   （阈值 85 都过不了）
边缘：(240, 90, 30)  → R−G = 150  （能过）
```
于是灯条只剩下**两边的边缘**，中间断开 → 碎成多块。

**为什么 `R−B` 稳定**：
```
中心：(255, 190, 40) → R−B = 215  ✅
边缘：(240, 90, 30)  → R−B = 210  ✅
白灯：(240, 240, 235) → R−B = 5   ✅ 自动排除
```

**代价**：`R−B` 对**纯橙色不发光的物体**（橙色衣服、贴纸）也会响应。

**什么时候该换**：如果场景里有大面积橙色非自发光物，需要用"饱和度 + 亮度联合门限"，或改用 HSV 的 S/V 组合。

## 2. 二值化：固定阈值 / Otsu / 自适应

| 方案 | 优点 | 在本数据上 |
|---|---|---|
| **Otsu 自动阈值** | 无需调参 | ❌ **会把阈值压到 10 量级，全图变前景** |
| 自适应阈值（局部） | 应对光照不均 | ⚠️ 灯条本身是亮点，局部窗口会把背景抬高 |
| **固定阈值 85（采用）** | 简单、可解释、稳定 | ✅ 白灯管 0~30、灯条 100~200，85 落在空档 |

**Otsu 为什么失效**：

Otsu 假设直方图是**双峰**（前景/背景各一峰）。但 2 ms 曝光下：

```
99% 的像素挤在 0~20（背景）
灯条只占 0.1% 的像素，在 150~220
→ 直方图是"极端长尾单峰"，不是双峰
→ Otsu 找一个"类间方差最大"的分割点，结果落在 10 附近
→ 整幅图都成了前景
```

**代价**：阈值 85 是**针对这份数据标定的**，换曝光参数就要重调。

**验证方法**（可复现）：把 `diff_threshold` 从 30 扫到 200，看检出率曲线，
在 70~110 有一个平台期 —— 85 取在平台中间，左移右移都稳定。

## 3. 形态学核：方形 / 竖长条 / 各向异性

| 方案 | 效果 |
|---|---|
| 3×3 方形开运算 | ✅ 去噪点，成本低（采用） |
| 17×17 方形闭运算 | ❌ **会把左右两根灯条粘成一块** → 从漏检变错检 |
| **3×17 竖长条闭运算** | ✅ 补竖向断裂，不粘连（采用，最终 3×23） |
| 横向长条 | ❌ 灯条是竖的，横向核无意义 |

**为什么必须"竖长条"**：灯条是**竖直细条**，它的断裂必然发生在**竖直方向**
（数字遮挡、JPEG 的 8×8 块效应、LED 灯珠间隙）。而左右相邻的两根灯条之间是**水平间隙**。

```
竖核 3×23：只补竖向缺口，不会跨过水平间隙    ✅
方核 23×23：会同时跨过水平间隙 → 两根灯条粘一起  ❌
```

**核高 23 是怎么定的** —— 阈值扫描：

| 核高 | 检出率 |
|---|---|
| 9 | 59% |
| 13 | 59% |
| 17 | 78.5% |
| 21 | 87.5% |
| **23** | **88.5%** |
| 25 | 88.5%（不再涨） |

从 21 开始饱和 → 说明缺口都补上了，加倍也没用。**取 23 而不是 25，因为更大的核会开始吞掉邻近结构。**

## 4. 轮廓提取：CHAIN_APPROX_NONE / SIMPLE

| 方案 | 返回点数 | 后果 |
|---|---|---|
| `CHAIN_APPROX_NONE` | 边界上**每一个**像素（70×13 灯条约 166 点） | 宽度撑大 1 px、PCA 主轴被锯齿带偏 |
| **`CHAIN_APPROX_SIMPLE`（采用）** | 只保留拐角（8 个左右） | 尺寸准确、方向稳定 |

**具体损失**：

```
宽度 13 px 的灯条，多算 1 px = 8% 误差
长宽比从 3.9 掉到 3.6 → 接近下限 1.5 的窄灯条被筛掉
PCA 主轴被像素阶梯带偏几度 → 撞上配对的 10° 角度限制
```

**实测**：同一份数据，只切这一个参数，`SIMPLE` 得 85%、`NONE` 得 75%（**+10 个点**）。

**什么时候该用 NONE**：需要逐像素形态时（算周长、轮廓匹配、凸缺陷分析）。我们只用拐角几何，用不到。

## 5. 灯条方向：minAreaRect / PCA

| 方案 | 原理 | 稳定性 |
|---|---|---|
| `minAreaRect().angle` | 最小外接旋转矩形的角度 | ❌ 破碎轮廓上会被噪声带偏几度 |
| **PCA / `fitLine`（采用）** | 全部轮廓点的主方向 | ✅ 拟合整体点云，稳得多 |

**为什么 `minAreaRect` 不稳**：它只关心"能框住所有点的最小旋转矩形"。
轮廓末端缺一小角，矩形的角度就会跳 —— 而配对要求两根灯条角度差 ≤ 10°，几度误差就误杀。

**PCA 为什么稳**：它用**所有点**的协方差矩阵求主方向，个别点的缺失只造成很小扰动。

**实现**：`cv::fitLine(points, line, DIST_L2, 0, 0.01, 0.01)` —— [OpenCV] 内置最小二乘直线拟合，
输出方向向量。归一化后就是灯条的轴方向。

## 6. 配对判据：几何约束怎么选

| 判据 | 值 | 为什么是这个值 | 依据 |
|---|---|---|---|
| 长度比 | ≤ 1.25 | 同一块板的两根灯条等长；透视下最多差 30% | 实测真配对 ≤1.10、跨板误配 1.27~1.52 |
| 中心距/平均长度 | 1.2~4.2（理想 2.2） | `(135−12)/56 = 2.20` | 几何算出来的 |
| 角度差 | ≤ 10° | 同一块板上的灯条平行 | 真配对 ≤3°、跨板 11~18° |
| 连线垂直于灯条 | ≤ 25° | 两根是"并排"的 | 旋转不变量，比 `abs(dy)` 稳 |
| 四边形宽高比 | 1.4~3.2 | `135:56 = 2.41` | 太宽说明把两块板各取一根配到一起 |

**为什么中心距用"区间 + 打分"而不是"等于 2.2"**：

**透视投影不是相似变换**。斜着看时，两根灯条的间距会被压缩，比值会跟着变。
所以只能说"在 1.2~4.2 之间"，再在这个范围里挑"最接近 2.2 的"。

打分公式：

```
score = |长度比−1| + |中心距比−2.2| + 角度差/10 + 横向偏差/25
```

实测分布：**真装甲板 0.30~0.62，背景假配对 1.14~1.72** → 门限 1.2 落在中间。

**代价**：门限 1.2 会切掉一部分"桥接（过渡帧）"的检测，实测牺牲约 1 个百分点检出率，换来背景误检从"偶发"降到 0.27%。

## 7. 角点来源：端点 / 直线求交 / 亚像素

| 方案 | 精度 | 问题 |
|---|---|---|
| 直接取灯条端点 | 低 | **四次独立测量**，任一端点抖动直接进 PnP |
| **直线求交（采用）** | 高 | 每个角被两条线共同约束 |
| 直线求交 + **亚像素精化（采用）** | 最高 | 重投影误差 0.441 px |

**构造方法**：

```
每根灯条：u = 轴线（PCA）、n = 外法线
          外缘线 = 过 (中心 + n×半宽)、方向 u
上下边界：过两根灯条的"外缘顶点"，方向垂直于两根灯条方向的平均值
四个角点 = 左右外缘线 × 上下边界线 的交点
```

**两个刻意的设计选择**：

1. **左右两边不强制平行**
   真实透视下矩形呈现为**一般四边形**（近大远小，两边收敛）。强加平行会引入系统偏差。

2. **上下边方向用两根灯条方向的平均值**
   上下边必须垂直于灯条（矩形的事实），用平均值能把各自的几度噪声**平均掉一半**。

**效果**：重投影误差 **1.0 px → 0.441 px**（−56%）。

**亚像素的安全措施**：如果某个角点移动超过 `max_shift_px`（说明锁到了错误的边），
**整个精化结果丢弃**，保留原角点 —— 宁可不动，不能动错。

## 8. PnP 解法：EPnP / 迭代 / IPPE / P3P

| 方案 | 适用 | 优点 | 缺点 |
|---|---|---|---|
| `SOLVEPNP_ITERATIVE` | 通用 | 精度高 | 需初值；可能局部极小 |
| `SOLVEPNP_EPnP` | 通用 | 无需初值、快 | 非共面假设，共面时退化 |
| `SOLVEPNP_P3P` | 3 点 | 快 | **最多 4 组解**，且需要恰好 3 点 |
| **`SOLVEPNP_IPPE`（采用）** | **共面点** | 解析解、无需初值、稳定 | 只处理共面 |

**为什么选 IPPE**：我们的四个角点**严格共面**（都在装甲板平面上），
IPPE 就是为这个场景设计的解析解法。它返回**两组解**（平面镜像歧义），
我们再逐组算重投影误差、取小的那组，并要求 `tvec.z > 0`。

**为什么不用 P3P**：P3P 用 3 个点就有解，但**最多 4 组解**，歧义更严重；
而且我们明明有 4 个点，用 4 个点（8 个方程解 6 个未知数）更稳。

**最后一步 `solvePnPRefineLM`**：在初值附近最小化重投影误差（LM 迭代），
把角点噪声的影响压到最小。

**输出**：`rvec`（旋转向量）、`tvec`（平移向量）、`reproj_err_px`。

## 9. 位姿可信度：重投影误差 vs 其他

| 方案 | 说明 | 评价 |
|---|---|---|
| 不检查 | 有解就用 | ❌ 跨板误配也会给出一个"看起来正常"的位姿 |
| 检查 Z 范围 | `1 < z < 16` | ⚠️ 太粗，错配的 Z 也在这个范围 |
| 检查姿态角 | pitch 合理 | ❌ pitch 本身不可观（噪声 15.9°） |
| **重投影误差（采用）** | 把 3D 点投回图像，比像素距离 | ✅ 直接衡量"位姿能不能解释观测" |

**为什么重投影误差最合适**：它是**自洽性检验** ——
"用你估的位姿把角点投回去，能不能盖住实际检测到的角点"。这是唯一不依赖外部真值的质量指标。

**门限 2.5 px 的依据**：正常帧 < 1.2 px（实测中位 0.442）；跨板误配 > 3 px。
取 2.5 在两者之间。

**代价**：约 0.5% 的帧因为角点抖动被丢弃。**这是有意的** —— 自瞄里错误的坐标比没有坐标更危险。

## 10. 测量与显示分离

**这是我犯过的一个真实错误，值得单独写一节。**

| 方案 | 结果 |
|---|---|
| **用同一个 `plate_edge_offset` 同时控制 PnP 和显示** | ❌ 为了框好看改成内缘 → PnP 系统性偏小 → 距离高估、误差从 0.44 涨到 0.755 |
| **物理量与显示量分开（采用）** | ✅ `plate_edge_offset=+1`（PnP 用外缘）、`draw_inset_ratio=0.09`（只影响画面） |

**为什么必须分开**：

- 物理事实：135 mm 是**灯条外缘到外缘**的距离
- 如果用内缘算 PnP，等于告诉它"这块板只有 120 mm 宽"，而实际是 135 mm
- 结果：**系统性失配**，重投影误差涨 70%，检出率掉 2.6 个点

**拆分后的参数表**：

| 参数 | 管什么 | 影响精度 |
|---|---|---|
| `plate_edge_offset` | PnP 用的角点位置 | ✅ 影响 |
| `armor_height_m` | PnP 的物体点高度 | ✅ 影响 |
| `draw_inset_ratio` | 只在画面上左右内收 | ❌ 不影响 |
| `draw_extra_height_ratio` | 只在画面上上下加高 | ❌ 不影响 |
| `draw_inflate_px` | 只在画面上整体外扩 | ❌ 不影响 |

**通用原则**：**"测量的起点"和"显示的样式"必须是两个独立的量。**
一旦共用一个参数，就会出现"改画面把数据改坏"的连锁反应。

## 11. 抗干扰：五层过滤怎么分配

| 层 | 手段 | 对付什么 | 实测依据 |
|---|---|---|---|
| 像素层 | `R−B` + 亮度门限 | 白色背景灯 | 白灯 `R≈G≈B`，差值趋 0 |
| 形状层 | 面积/长宽比/填充率/倾角 | 圆形光斑、横置灯管 | 灯条 56×12，长宽比 4.7 |
| 组合层 | 长度比/平行度/间距比/宽高比 | 不像装甲板的配对 | 见 §6 |
| 统计层 | `score ≤ 1.2` | 几何凑合的假配对 | 真 0.30~0.62 / 假 1.14~1.72 |
| **尺寸层** | **像素宽度 ≥ 45 px** | **体积远小于真实目标的候选** | 真 min 55.6 px / 假 max 23.2 px |
| **时序层** | 连续 3 帧一致 | 只出现一两帧的偶然候选 | 帧间位移 p50=1.9 px |

**一个失败的尝试（重要）**：

我最初加了"两根灯条亮度比 ≤ 1.35"，理由是"同一块板由同一路 LED 驱动"。
**物理上完全合理，但实测是错的**：

| 特征 | 真装甲板 | 疑背景 |
|---|---|---|
| 亮度比 p95 | **1.47** | **1.11** |
| 亮度比 max | 2.28 | 1.18 |

**背景的亮度反而更一致** → 这个特征没有区分度。
在 1.35 下：挡掉 0 个背景，误杀 67/423 个真目标（16%），检出率直接掉 12.5 个点。

**教训（本工程最重要的一条）**：

> 判断一个特征能不能用，标准**不是**"它在物理上是否合理"，
> 而是**"两类样本的分布有没有重叠"**。
>
> - 有重叠 → 收紧就误杀、放松就没用，**不能当硬阈值**
> - 有空档 → 阈值放空档中间，两边都不碰，非常可靠

**尺寸特征的空档**：真目标最小 55.6 px、背景最大 23.2 px → **空档 32 px 宽**，45 落在正中。

## 12. 时序确认：单帧 / N 帧 / 多判据状态机

| 方案 | 能解决的问题 | 缺点 |
|---|---|---|
| 单帧（无历史） | — | 无法区分"真目标"和"偶然凑成的四边形" |
| 连续 N 帧命中 | 挡掉瞬时误检 | ❌ 目标丢失时立刻甩丢 |
| **多判据状态机（采用）** | 挡住误检 + 抗遮挡 | 需要调参 |

**采用的方案**：四态状态机

| 状态 | 条件 | 输出 |
|---|---|---|
| `confirmed` | 连续 3 帧关联上 | ✅ 坐标可输出 |
| `predicted` | 丢失但在 5 帧容忍期内 | ❌ 但目标不甩丢 |
| `tentative` | 有候选但帧数不够 | ❌ |
| `none` | 无候选 | ❌ |

**三个关联判据**（同时满足才算同一目标）：

| 判据 | 门限 | 物理含义 | 实测余量 |
|---|---|---|---|
| 中心像素距离 | ≤ 60 px | 6 ms 内移动不了几像素 | 帧间位移 max 3.4 px（**18 倍**） |
| 四角宽度比 | ≤ 1.4 | 宽度 = `fx×0.135/d`，等价于距离比 | 帧间宽度比 max 1.035（**40 倍**） |
| 米制距离 | ≤ 0.6 m | 像素判据近距离不灵敏，补一维 | — |

**为什么三个都要**：像素判据在目标**近**时不灵敏（目标大，走 0.6 m 只移动几像素），
在**远**时又太灵敏 —— 两个判据一个擅长近、一个擅长远。

**实测分布**：confirmed 80.2% / predicted 8.6% / tentative 2.3% / none 8.8%。
其中 `predicted 8.6%` 就是"短暂遮挡不甩丢"的直接证据。

**代价**：视频开头和目标重捕后有 2 帧空白（0.1%）。**自瞄里这个取舍是强制性的** ——
误报会让云台打偏，晚报 18 ms 目标才动 1.8 cm。

## 13. 速度优化：ROI / 降采样 / 多线程

| 方案 | 提速 | 代价 | 采用 |
|---|---|---|---|
| **ROI 复用** | detect 6.25 → 0.72 ms（**−90%**） | 需要跟踪；跟丢要回退 | ✅ |
| 降采样到 720p | 约 4 倍 | 角点精度掉一半 → 距离误差翻倍 | ❌ |
| 多线程（检测/匹配并行） | 1.2~1.5 倍 | 复杂度高，帧间依赖难拆 | ❌ |
| GPU | 10 倍+ | 需 CUDA；部署复杂 | ❌ |
| **只做算法优化，不动数据格式** | — | 解码仍占 6 ms | 接受 |

**为什么 ROI 能快 10 倍**：

```
全图 1440×1080 = 1,555,200 像素
窗口  400×400  =   160,000 像素  → 1/9.7 计算量
```

**为什么端到端只涨 1.8 倍**：MJPG 解码固定占 6 ms 左右
（1440×1080 每帧约 350 KB，166 fps = 59 MB/s）。**瓶颈不在算法**。

**检出率没掉的三个保护**：

1. 丢失期间窗口每次放大 **1.6 倍**（上限 600 px）
2. 连续丢失 > 3 帧 → 回退全图
3. 窗口里配不出装甲板 → **当场全图重试一次**

实测：`1554 帧用窗口 / 216 帧全图 / 214 次回退 / 107 次重试`，**检出率与全图完全一致（84.2%）**。

## 14. 卡尔曼：开 / 关，匀速 / 匀加速

| 方案 | 平滑收益 | 延迟补偿 | 采用 |
|---|---|---|---|
| 不开 | — | ❌ | 曾经是默认 |
| **匀速模型（采用）** | 166 fps 下接近 0 | ✅ 外推到击发时刻 | ✅ 默认开启 |
| 匀加速模型 | 略好 | 略好 | ❌ 加速度不可观测，噪声放大 |

**为什么 166 fps 下平滑收益接近零**：帧间隔只有 6 ms，目标在 6 ms 内几乎不动，
**没有东西可平滑**。实测开关前后检出率完全一样（84.2%）。

**它的真正价值是延迟补偿**：

```
p_pred = p_now + v × t_latency      t_latency 默认 20 ms
```

从曝光到真正击发有 20~40 ms 的延迟（传输 + 解算 + 开火指令），
这期间目标会移动 2~4 cm（1 m/s 时）。所以把位姿外推到击发时刻，画面上用橙色 `PRED` 点表示。

**为什么不显示预测坐标作为最终输出**：预测有模型误差，实测仍以 PnP 输出为准，
预测只用于"提前量参考"和 ROI 窗口。

## 15. 反陀螺：圆拟合 vs yaw 差分

| 方案 | 原理 | 稳健性 | 采用 |
|---|---|---|---|
| **圆周/椭圆拟合** | 装甲中心轨迹拟合圆，得圆心、半径、ω | ❌ 短弧病态（我踩了坑） | 作为"另外三块位置"的来源 |
| **yaw 差分（采用为主判据）** | 直接对 PnP 的 yaw 求时间导数 | ✅ 单帧可观、不依赖弧长 | ✅ 第一道判据 |
| 装甲板数字识别 | 识别 1~5 定相位 | ✅ 最准 | ❌ 无模型 |

**为什么 yaw 差分更可靠**：

- yaw 是 PnP 的**直接输出**，不像圆心那样需要拟合
- 不依赖"圆弧够长" —— 短时间也可靠
- 社区（[AutoAim_HUST](https://github.com/XianMengxi/AutoAim_HUST)、[sp_vision_25](https://gitcode.com/zjfklss/sp_vision_25)）普遍用它判陀螺

**实测证据**（A 段 1770 帧）：

```
|ω_yaw| 中位 49.3 deg/s   ← 目标没有自旋
|ω_yaw| p95  162.9 deg/s
|ω_yaw| 最大 404.5 deg/s  ← 单帧抖动
gyro_valid=1 的帧：0
```

**如果只看单帧**，那 404.5 的帧会被误判成陀螺；用**窗口拟合 + 符号一致 + 一步预测误差**就挡住了。

**有效性判据（六条，全过才输出）**：

| 判据 | 门限 | 作用 |
|---|---|---|
| yaw 角速度 | > 200 °/s | 第一道：没在转就直接排除 |
| 平面拟合残差 | < 5 cm | 点必须共面 |
| 半径物理先验 | 0.075 m ±45% | 装甲中心到转轴的真实距离 |
| 圆拟合 ω | > 150 °/s | 第二道 |
| ω 相对标准差 | < 25% | 转速必须稳定 |
| 圆心漂移 | < 8 cm | 转轴不能乱跑 |
| **一步预测误差** | **< 2 cm** | **模型要能预测下一帧的实际位置** |

最后一条最硬：它是"预测 vs 实测"的对照，不是在拟合数据本身。

**合成自检验证**：`./build/autoaim --gyro-selftest` 用已知真值的圆周轨迹
（圆心 (0,0,2)、半径 0.075 m、ω=500 °/s）验证，**误差全部 0.0**。

**这个自检抓出了 5 个 bug**（详见 `教程_改进思路与术语详解.md` §4）：
`projectPoints` 类型崩溃、判据循环依赖、病态早期估计污染统计、转轴符号随机翻转、窗口未满就拟合。

## 16. 未采用的方案清单及理由

| 方案 | 为什么不用 |
|---|---|
| **YOLO 检测** | 零标注；域差异（2 ms 极暗 vs 正常曝光）；灯条是自发光饱和目标，传统方法更合适 |
| **HSV 阈值** | H 是比值函数，暗处/过曝处不稳定；红色跨 0/179 边界 |
| **Otsu 自动阈值** | 暗场景直方图是极端长尾单峰，会被压到 10 量级 |
| **方核闭运算** | 会把左右灯条粘成一块 |
| **P3P** | 用 3 点有 4 组解，歧义比 IPPE 更严重 |
| **数字识别** | 时间不足；且它属于"兵种分类"，不影响位置精度 |
| **IMU 姿态补偿** | 基本要求只要相机系位置；外参已能解析（`--calib` 读 `R_camera2gimbal`），未使用 |
| **弹道解算/预测开火** | 超出考核范围；且需要子弹速度、空气阻力模型 |
| **降采样提速** | 角点精度掉一半，距离误差翻倍，与"提高精度"的目标冲突 |
| **多线程/GPU** | 瓶颈在 MJPG 解码（6 ms），不在算法 |
| **PID/云台控制** | 考核只要求"位置"，不要求执行机构控制 |
